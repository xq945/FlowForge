# 14 面试问答与设计决策

> 这份文档面向"讲清楚这个项目"。所有回答都对应仓库里真实存在的代码，
> 不确定的地方会写明「这是设计意图，没有实测」，不夸大。

## 一、三分钟讲清项目

**一句话**：FlowForge 是一个任务编排平台，用户把节点连成 DAG 工作流，平台负责触发、调度、执行、重试、留痕和通知。

**重点不在 CRUD，在执行过程中的意外**：

> 节点失败了要不要重试、重试几次；进程崩在"数据库已提交、消息还没发出去"的缝隙里怎么办；
> 两个调度实例同时扫到同一条到期任务怎么办；用户手抖点了两次执行，会不会跑出两份实例；
> 工作流改版发布后，昨天启动的执行该用新逻辑还是旧逻辑。

**我的做法是给每个问题一个可验证的答案**，而不是用布尔字段和分布式锁盖住：

| 问题 | 答案 | 代码位置 |
| --- | --- | --- |
| 重复提交 | `workflow_execution.uk_trigger` 唯一键 | `ExecutionEngine#createExecution` |
| 重复投递 | 节点状态条件更新 | `NodeExecutionMapper#claimForRun` |
| 消息丢失 | Transactional Outbox + 发布确认 | `OutboxWriter` / `OutboxPublisher` |
| 并发完成 | 实例行锁 + 条件更新终结 | `ExecutionEngine#completeNode` |
| 在途实例被改版影响 | 版本快照 + 不可变版本 | `WorkflowService#publish` |
| 卡住不结束 | 超时扫描 + 可达性重算 | `ExecutionTimeoutScanner` / `ExecutionGraph` |

## 二、高频追问

### Q1：为什么拆成 6 个服务？是不是过度拆分？

按**数据所有权**拆，不按技术层拆：用户、工作流定义、调度、执行、通知各自拥有独立的库。
跨服务的状态流转一律走消息，同步调用只用于「读快照」这类无副作用操作。

实际收益：执行服务的写压力与工作流的读压力互不影响；工作流服务挂了不影响已在跑的实例。

诚实的部分：**对这个规模，单体完全够用**。拆分的价值在于把「服务边界」「数据所有权」
这些约束显式化，而不在于性能。面试时不要假装微服务是必须的。

### Q2：DAG 校验都校验了什么？

`DagValidator` 分三层：

1. **结构**：key 格式与唯一性、节点类型合法、边的两端存在、不允许自环、不允许重复边
2. **拓扑**：Kahn 拓扑排序检环、至少一个起点、孤立节点（既无入边也无出边）
3. **配置**：按节点类型的白名单字段校验，HTTP 只允许 http/https

**草稿宽松、发布严格**：保存草稿只做第 1、3 层（编辑中间态经常还没连边），
发布时才跑全部。这个区分是实际做下来才意识到需要的——否则用户加了节点还没连线就存不了。

踩过的坑：最初用「能否从起点到达」判断孤立节点，但**入度为 0 的节点本身就是起点**，
可达性检查对它恒为真。后来改成直接判断「无入边且无出边」。

### Q3：条件分支是怎么跳过的？

条件节点执行完产出 `result=true/false`，引擎**每次节点完成后全局重算可达性**：

```
selectedEdges = 非条件边 ∪ 已确定的条件边中选中的那条
reachable = 从所有入度为 0 的节点沿 selectedEdges BFS
不可达的 WAITING 节点 → SKIPPED
```

为什么不用增量传播：增量方案要维护「汇合点是否还有分支会汇入」的入边计数，
嵌套条件时边界情况非常多；全局重算规则只有一条，节点数在百级以内开销可忽略。

**未执行的条件节点，两条分支都保持可达**——过早判死会让尚未确定的分支被误跳过。

### Q4：节点状态机怎么防止并发覆盖？

所有迁移都是带前置状态条件的 UPDATE：

```sql
UPDATE node_execution SET status='RUNNING'
 WHERE id=? AND status='READY'
```

影响行数为 0 就放弃——说明已被别的线程/实例抢占，这是正常幂等场景，不是错误。

推进后继逻辑在**实例行的行锁内**执行（`SELECT ... FOR UPDATE`），
多个节点同时完成也不会让实例状态互相覆盖。

### Q5：Transactional Outbox 解决什么问题？

**数据库提交成功、消息还没发出去的崩溃窗口**。

做法：业务变更与 `outbox_event` 在同一个本地事务提交；发布器扫 `PENDING` 事件，
发到 RabbitMQ 并**同步等待 Publisher Confirm**，ack 且没有 Return 才标记 SENT。

它能保证什么：**可恢复的至少一次投递**。
它不能保证什么：**不重复**。进程在"发送成功但没来得及标记 SENT"时崩溃，就会重发。
所以消费端必须幂等——这不是可选项。

题外话：没用 `SKIP LOCKED` 领取事件，多实例同时发布会重复投递，
但因为消费端幂等，这属于可接受的冗余。

### Q6：重试为什么有"两层"？

| 层级 | 触发 | 载体 | 兜底 |
| --- | --- | --- | --- |
| 节点级 | 节点业务失败（HTTP 5xx、连接失败） | `RETRY_WAIT` + `next_retry_at` | 扫描器 |
| 消息级 | 消费过程异常（DB 抖动） | 延迟队列（5s/30s/2m） | 死信 |

关键点：**延迟队列是加速器，扫描器是兜底**。消息丢了，扫描器还能把 `RETRY_WAIT`
的节点捡回来继续推进——**数据库始终是事实来源**。

为什么不用 `basicNack(requeue=true)`：数据库抖动时消息会在热门队列里无限打转，
占满消费线程并打爆日志。所有重试都必须经过延迟队列并带次数上限。

### Q7：为什么不用 Redis 分布式锁？

因为**锁和事务的边界对不齐**：锁释放后事务可能还没提交，或者反过来，
必须额外加"锁内校验 + 数据校验"才安全。而数据库唯一键一次到位，故障时也不会残留死锁。

Redis 在本项目只做缓存与限流计数——**失败了也不影响正确性**的那些场景。

### Q8：为什么不用 Seata？

跨服务一致性用「本地事务 + Outbox + 消费幂等」解决，引入协调者只会增加故障面。

具体来说，本项目没有**跨库事务**需求：每个服务只写自己的库，
服务之间的状态流转通过消息达成最终一致。XA 是为"必须同时成功"的场景准备的，
而这里的业务语义本来就是"允许秒级延迟"。

### Q9：工作流发布后又被改，在途执行怎么办？

**版本快照 + 不可变版本**：实例创建时绑定 `workflow_version_id`，
节点、边、配置全部挂在版本上，草稿是另一条 `version_no=0` 的记录。

执行服务运行时不回查工作流服务——调度服务取到快照后随请求传给执行服务，
实例的 `node_execution.config_snapshot` 和 `workflow_execution.edges_snapshot`
让它**自包含**。工作流后续被编辑、重新发布、甚至删除，都不影响在途实例。

### Q10：停用工作流会影响正在跑的实例吗？

不会。停用只改 `workflow_definition.status`，只拦截**新的触发**。
在途实例继续按启动时的版本跑完，要终止得走取消接口（协作式，不强杀节点）。

### Q11：节点执行超时，外部接口可能已经成功了，怎么办？

错误分类为 `HTTP_RESULT_UNKNOWN`，`execution_attempt.uncertain=1`，**默认不自动重试**，
通知里提示"结果未知，请人工确认"。

如果节点显式开启 `retryOnUncertain`，重试请求必须携带幂等键，由对端去重。

核心认识：**幂等键依赖对端支持**。如果第三方接口不支持，无论怎么重试都无法保证不重复——
这是能力边界，不是设计缺陷。

### Q12：消息里都放了什么？为什么只放 ID？

统一信封：`eventId`、`eventType`、`occurredAt`、`traceId`、`executionId`、
`nodeExecutionId`、`workflowVersion`。

只放定位记录需要的 ID，不放业务载荷与任何凭证。消费端拿到 ID 自己去库里读——
这样消息体积小，也不会因为消息里存了过期数据而产生歧义。

### Q13：网关鉴权了，业务服务还要校验吗？

要，而且**业务服务不信任网关传来的身份头**。

每个服务都独立解析 JWT 签名建立身份。攻击者若能绕过网关直连服务端口，
伪造 `X-User-Id` 是无效的。网关的作用是**快速拒绝**，不是**授权**。

同理，前端的按钮隐藏只是体验优化，权限判断始终在后端。

### Q14：XXL-JOB 用来做什么？为什么不用 @Scheduled？

`@Scheduled` 在多实例下每个实例各跑一遍。XXL-JOB 由调度中心统一决定谁来跑。

但注意：**即便如此，防重复也不依赖调度框架**。真正的兜底是
`schedule_execution.uk_job_fire (job_id, fire_time)` 唯一键——
不假设调度中心永远只触发一次。

周期任务的设计：XXL-JOB 每分钟触发一次"扫描到期任务"的心跳，
具体每个任务什么时候跑由 `schedule_job.cron_expr` 决定。停机错过的周期**直接跳过**，
不做补偿——补偿会让停机越久、恢复时洪峰越猛烈。

### Q15：实例超时靠什么判定？

不靠内存计时器——进程崩了计时器就没了。靠数据库里的 `deadline_at`，
由 `ExecutionTimeoutScanner` 每 5 秒扫描一次。

超时后把**未执行**的节点置 CANCELLED，正在跑的节点任其结束（结果会被丢弃），
保证实例一定能收敛到终态而不是永远挂在 RUNNING。

### Q16：版本兼容性怎么确认的？

没有盲选最新版，而是从 Maven Central 查实际发布的 BOM 内容确认对应关系：

- Spring Cloud Alibaba `2025.0.0.0` 的父 BOM 是 `spring-cloud-dependencies-parent 4.3.0`
  （即 Spring Cloud 2025.0.x 线）
- 该 BOM 内置 `nacos-client 3.0.3`，所以服务端固定 `nacos-server v3.0.3`
- Springdoc 必须用 2.x（3.x 面向 Boot 4）

踩过的坑：Spring Cloud Gateway 在 2025.0 里实际是 `4.3.x`（不是 5.x），
artifact 名为 `spring-cloud-starter-gateway-server-webflux`。

## 三、可以写进简历的三条

1. **设计并实现 DAG 执行引擎**：以「全局重算可达性」实现条件分支跳过，
   用条件更新 + 实例行锁保证多节点并发完成时的状态一致性。
2. **解决分布式消息可靠性问题**：引入 Transactional Outbox + 发布确认 + 消费幂等，
   并用延迟队列与扫描器双层兜底，覆盖"数据已提交但消息未发出"的崩溃窗口。
3. **建立可验证的故障恢复机制**：实例超时、服务熔断、毒消息死信均有对应扫描器与留痕，
   用故障注入实测验证 7 类异常场景下的数据状态。

## 四、被问到"这个项目有什么不足"时

诚实回答（这些都是真实存在的）：

1. **多实例竞争只有设计保证，没有真实复现**。双实例压测、kill 进程验证 Outbox 补发
   都还没做，目前靠唯一键和行锁的语义保证正确性。
2. **没有 Testcontainers 自动化集成测试**，集成验证是手工跑容器环境完成的，
   回归成本高。
3. **节点配置与运行环境耦合**。容器化时发现 HTTP 节点写死 `127.0.0.1` 会失败，
   目前靠"用服务名"的约定解决，没有做配置变量化。
4. **Outbox 发布器未做 SKIP LOCKED 领取**，多实例会重复发布（靠消费端幂等兜底）。
5. **前端体积 1.1MB 未按需分包**，首屏偏慢。
