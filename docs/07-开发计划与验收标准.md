# 07 开发计划与验收标准

## 1. 阶段总览

| 阶段 | 主题 | 主要产出 | 完成标志 |
| --- | --- | --- | --- |
| 一 | 需求与架构设计 | 本目录 7 份文档 | 用户确认设计 |

每个阶段结束时提交一次可运行的代码，并输出该阶段的**验收报告**（做了什么、怎么验证的、还剩什么）。未实际执行的验证一律标注"待验证"。

## 3. 阶段三：核心业务开发

### 3.1 任务拆解

| 序号 | 任务 |
| --- | --- |
| 3.1 | workflow-service：工作流 CRUD、节点、边、版本表与发布流程 |
| 3.2 | DAG 校验：环检测、悬空引用、起始节点、条件边完整性、配置白名单 |
| 3.3 | scheduler-service：手动执行入口、版本快照读取、实例创建（含幂等） |
| 3.4 | execution-service：节点初始化、READY 判定、可达性重算、条件分支 SKIPPED |
| 3.5 | 节点执行器：HTTP、条件、模拟业务、通知四类 |
| 3.6 | 执行查询接口：实例列表、详情、节点明细、尝试记录 |

### 3.2 验收标准

| 验收项 | 验证方式 | 通过标准 |
| --- | --- | --- |
| 发布校验 | 构造带环、悬空边、空的 DAG 各一次 | 分别返回明确错误码与节点定位 |
| 完整执行 | 创建 4 节点工作流（HTTP → 条件 → 模拟 → 通知）并执行 | 实例 SUCCESS，节点状态符合预期 |
| 条件分支 | 构造 TRUE / FALSE 两条路径分别执行 | 未选中分支节点为 SKIPPED，实例正常终结 |
| 版本隔离 | 实例执行中发布新版本 | 在途实例仍按旧版本节点执行 |
| 重复执行 | 同一 `requestId` 请求两次 | 只产生一个实例，第二次返回同一实例 |
| 失败路径 | 模拟节点配置 100% 失败 | 节点 FAILED，下游 CANCELLED，实例 FAILED |

此阶段**允许先用同步调用实现闭环**（执行服务内部直接调用节点执行器），但表结构、状态机、幂等约束必须按最终设计落地，阶段四只替换"驱动方式"，不改数据模型。

## 4. 阶段四：微服务可靠性

### 4.1 任务拆解

| 序号 | 任务 |
| --- | --- |
| 4.1 | Outbox 表、发布器、Publisher Confirm、Return 处理 |
| 4.2 | RabbitMQ 拓扑声明、延迟队列、死信队列 |
| 4.3 | 消费端幂等、手动 ACK、异常分类 |
| 4.4 | 节点级重试与退避、重试扫描器 |
| 4.5 | 实例级超时、取消、对账任务 |
| 4.6 | XXL-JOB 接入：执行器、任务创建、cron 回调 |
| 4.7 | Feign 超时、Resilience4j 熔断 |
| 4.8 | 通知服务：消费 `workflow.finished`、幂等落库、已读 |

### 4.2 验收标准（全部需要实际执行并记录）

| 场景 | 注入方式 | 预期结果 |
| --- | --- | --- |
| 重复调度 | 同时触发两个调度实例处理同一 `job+fireTime` | 只创建一个实例，另一条 `schedule_execution` 插入失败被忽略 |
| Outbox 补发 | 发布前 kill 发布器 / 关闭 RabbitMQ 后再恢复 | 事件最终 SENT，节点最终执行 |
| 重复消费 | 同一消息手动投递两次 | 节点只执行一次，第二次 ACK 丢弃 |
| 消费崩溃 | 处理中断开消费者连接 | 消息重投，状态一致 |
| 重试退避 | 配置初始 1s、最大 3 次 | `next_retry_at` 序列符合 `1s → 2s → 4s` |
| 死信 | 持续失败至超过上限 | 进入 `q.node.dead`，`dead_letter_record` 有记录 |
| 实例超时 | 配置 5s 超时 + 慢节点 | 实例 TIMED_OUT，未完成节点 CANCELLED |
| 熔断 | 关闭 workflow-service 后执行 | 快速失败并返回明确错误，不长时间挂起 |

## 7. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| Nacos 3.x 默认开启鉴权，配置项与 2.x 不同 | 服务注册失败 | 阶段二第一件事就打通注册，不拖到后面 |
| XXL-JOB 3.5.0 需要自行构建 admin 镜像 | 环境搭建耗时 | 阶段四再接入；阶段三用手动触发验证闭环 |
| Spring Cloud Gateway 2025.0.x 有 WebFlux / WebMVC 两种实现 | 选错导致路由不通 | 第一版用 WebFlux 版，`spring-cloud-starter-gateway-server-webflux` |
| Windows 下 Docker 卷挂载路径与换行符 | 初始化 SQL 执行失败 | SQL 文件统一 LF，挂载用相对路径 |
| 版本组合只在文档层面验证过 | 实际构建可能冲突 | 阶段二第一件事跑 `dependency:tree`，冲突即调整并更新本文档 |

## 9. 验收标准（项目最终）

1. 按文档从零启动，不需要手工修改配置。
2. 能创建、校验、发布工作流，版本历史可查。
3. 能手动触发与定时触发执行。
4. 多节点、条件分支、跳过逻辑符合状态机定义。
5. 执行详情能看到每个节点的每次尝试与错误原因。
6. 失败重试、死信、通知均有可验证的结果。
7. 服务间通过 Nacos 发现，Feign 调用有超时与熔断。
8. 重复提交、重复消息、并发扫描的测试用例全部通过。
9. 能讲清楚任意一个故障场景下数据为什么是正确的。
10. 代码结构清晰，公共模块没有变成共享数据库。

> 只有**实际运行过**的验证才能标记为通过。设计文档里的"预期结果"不是测试结论。
