# 06 并发与一致性方案

## 0. 总原则

1. **数据库是唯一事实来源**。任何"某个节点/实例现在是什么状态"的问题，答案只从 MySQL 取。
2. **能用唯一约束和条件更新解决的，不用锁**。约束由数据库原子性保证，锁需要处理超时、续期、所有权与脑裂。
3. **Redis 不承担关键互斥**。它只在限流、缓存、验证码这类"失败了也不影响正确性"的场景出现。
4. **所有恢复都靠扫描对账**，不依赖内存中的定时器——进程会崩，内存计时器会消失。

## 1. 十个关键场景

### 场景 1：用户连点两次执行，重复创建实例

| 项 | 内容 |
| --- | --- |
| 现象 | 用户双击"执行"按钮，或网络重试导致同一请求到达两次，产生两个执行实例，同一工作流跑两遍 |
| 机制 | `workflow_execution.uk_trigger (trigger_type, trigger_key)` |
| 做法 | 前端每次点击生成 `requestId`，作为 `trigger_key`；服务端 INSERT 冲突（`DuplicateKeyException`）后，按 `trigger_key` 查回已存在实例直接返回 `200` |
| 解决 | 完全消除重复实例，且不依赖任何锁 |
| 不解决 | 用户**刷新页面后重新点击**会生成新 `requestId`，这是两次真实意图，应当执行两次。系统无法也不应该去猜测用户意图 |
| 恢复 | 无需恢复，天然幂等 |

### 场景 2：多个调度实例同时扫描到期任务

| 项 | 内容 |
| --- | --- |
| 现象 | scheduler-service 部署 2 个实例，都扫到 `next_fire_time <= NOW()` 的同一条任务，都去创建执行实例 |
| 机制 | ① `SELECT ... FOR UPDATE SKIP LOCKED` 领取；② `schedule_execution.uk_job_fire (job_id, fire_time)` |
| 做法 | 领取时用 `SKIP LOCKED` 跳过已被其他实例锁住的行；创建执行记录时用唯一键兜底，冲突的一方放弃并记录 |
| 解决 | 双重保险：`SKIP LOCKED` 减少竞争，唯一键保证最终正确 |
| 不解决 | XXL-JOB 自身的调度分片不在本层控制，若 XXL-JOB 配置了多实例广播，仍可能重复回调——由唯一键吸收 |
| 恢复 | 调度失败（如 Feign 调用 workflow 服务超时）时，`schedule_execution.status=FAILED`，由对账任务在下一轮重新创建 |

**为什么不加 Redis 分布式锁**：锁与事务的边界永远对不齐——锁释放后事务可能还没提交（或者反过来），必须额外引入"锁内校验 + 数据校验"。唯一键一次到位，且故障时不会残留死锁。

### 场景 3：两个消费者同时处理同一节点消息

| 项 | 内容 |
| --- | --- |
| 现象 | RabbitMQ 重复投递（见场景 6），或消费者处理慢导致消息超时重投，两个消费线程同时处理 `node_execution_id=8801` |
| 机制 | 条件更新 `WHERE id=? AND status='READY'`；`execution_attempt.uk_node_attempt` |
| 做法 | 抢占 `READY → RUNNING` 只有一个成功；若两者都进入执行阶段（极小概率），尝试记录的唯一键 `(node_execution_id, attempt_no)` 会让第二个写入失败，从而整体回滚 |
| 解决 | 节点逻辑最多执行一次并留下记录 |
| 不解决 | **外部副作用无法回滚**。若两个线程都真的发出了 HTTP 请求，对方系统已经执行了两次——数据库只能保证我们自己的状态正确 |
| 恢复 | 对不确定的重复副作用，依赖 `Idempotency-Key` 请求头让对端去重（见场景 9） |

### 场景 4：节点完成，但进程在发送后续消息前崩溃

| 项 | 内容 |
| --- | --- |
| 现象 | 节点 SUCCESS 已落库，`node.ready` 消息尚未发出，进程被 kill，后继节点永远停在 WAITING |
| 机制 | Transactional Outbox + 发布器扫描 |
| 做法 | 业务变更与 `outbox_event` 同事务提交；发布器每 200ms 扫 `status=PENDING` 补发 |
| 解决 | 消息最终一定会发出，最多延迟一个扫描周期 |
| 不解决 | 消息延迟期间，用户看到的是"工作流卡住"的中间态，需要有监控与 UI 提示 |
| 恢复 | 自动恢复；另设兜底：扫描 `status='READY'` 超过 60 秒仍未被消费的节点，补一条 Outbox 记录 |

### 场景 5：数据库提交成功，但 RabbitMQ 发布失败

| 项 | 内容 |
| --- | --- |
| 现象 | 事务已提交，`rabbitTemplate.send()` 抛异常或 Confirm 返回 nack |
| 机制 | Outbox 状态机 `PENDING → SENT / FAILED` + 指数退避重发 |
| 做法 | 失败时 `retry_count++`，按 `next_retry_at` 退避重试；超过 10 次标记 `FAILED` 并告警 |
| 解决 | 短暂故障（Broker 重启、网络抖动）自动恢复 |
| 不解决 | Broker 长时间不可用会导致 Outbox 表积压，业务延迟累积——这是**正确的降级行为**：宁可延迟，不可丢失 |
| 恢复 | Broker 恢复后自动消费积压；`FAILED` 事件需人工介入（查看 `last_error` 后手动重置为 `PENDING`） |

### 场景 6：RabbitMQ 重复投递相同消息

| 项 | 内容 |
| --- | --- |
| 现象 | Confirm 后进程崩溃导致重复发布；或消费端 ACK 前崩溃导致重投 |
| 机制 | 消费端幂等（条件更新 / 唯一约束） |
| 做法 | `NODE_READY` 靠状态条件更新去重；`WORKFLOW_FINISHED` 靠 `notification_record.uk_source_event` 去重 |
| 解决 | 重复消息不产生重复业务结果 |
| 不解决 | 重复消费本身是不可避免的，只是被无害化处理。**"消息只来一次"从来不是前提** |
| 恢复 | 无需恢复 |

### 场景 7：工作流被停用时，仍有实例在执行

| 项 | 内容 |
| --- | --- |
| 现象 | 用户停用了工作流，但昨天启动的执行实例仍在跑 |
| 机制 | 状态隔离：停用只改 `workflow_definition.status`，执行实例读的是**版本快照**，不受定义状态影响 |
| 做法 | 执行服务全程不回查 `workflow_definition`；只有调度入口校验停用状态 |
| 解决 | 在途实例继续按启动时逻辑跑完，语义清晰 |
| 不解决 | 用户想立即终止在途实例时，只能走"取消执行"接口，且是**协作式**的（见 03 文档第 7 节） |
| 恢复 | 不涉及数据修复 |

### 场景 8：工作流版本更新，旧实例仍在执行

| 项 | 内容 |
| --- | --- |
| 现象 | 用户发布 v4，但 v3 的实例还在跑，可能读到新配置导致逻辑混乱 |
| 机制 | 版本绑定 + 发布版本不可变 |
| 做法 | 实例创建时记录 `workflow_version_id`；节点与边挂在版本上，`PUBLISHED` 版本禁止修改；执行服务只按 `workflow_version_id` 读数据 |
| 解决 | 在途实例永远按启动时的图与配置执行 |
| 不解决 | 若 v4 修复了 v3 中的严重缺陷，在途 v3 实例仍会用旧逻辑跑完——这是刻意选择，避免"运行中途换规则" |
| 恢复 | 用户可取消旧实例，再用新版本手动重跑 |

### 场景 9：节点执行超时，但外部请求可能已成功

| 项 | 内容 |
| --- | --- |
| 现象 | HTTP 节点请求已发出，读超时，无法判断对端是否处理完成 |
| 机制 | 错误分类为 `HTTP_RESULT_UNKNOWN` + `execution_attempt.uncertain=1` + 幂等键 |
| 做法 | 默认**不自动重试**，节点 FAILED 并在通知里提示人工确认；若节点显式开启 `retryOnUncertain`，重试请求携带 `Idempotency-Key: {executionId}:{nodeKey}` |
| 解决 | 避免在不确定的情况下重复制造外部副作用 |
| 不解决 | 幂等键依赖对端支持。如果第三方接口不支持，无论我们怎么重试都无法保证不重复 |
| 恢复 | 人工核对对端记录后，使用"手动重试"接口，并携带同一幂等键 |

### 场景 10：多个节点并发完成，实例状态竞争

| 项 | 内容 |
| --- | --- |
| 现象 | 并行分支的 3 个节点几乎同时完成，各自都去判断"工作流是否结束"，可能重复发布 `workflow.finished`，或互相覆盖状态 |
| 机制 | 原子计数 + 条件更新终结 |
| 做法 | ① `UPDATE workflow_execution SET finished_nodes = finished_nodes + 1 WHERE id=?` 原子自增；② 回读后若 `finished_nodes = total_nodes`，执行 `UPDATE ... SET status=? WHERE id=? AND status='RUNNING'`；③ 只有条件更新成功的那个线程负责写 `workflow.finished` |
| 解决 | 终结判定与通知发布都只发生一次 |
| 不解决 | 计数正确依赖"每个节点只在进入终态时自增一次"——这由节点状态机的条件更新保证（同一节点不可能两次从非终态进入终态） |
| 恢复 | 若实例因崩溃卡在"计数已满但未终结"，对账任务可重算 `finished_nodes` 并补终结 |

**失败传播**：节点进入 `FAILED` 时，把其下游可达且非终态的节点置 `CANCELLED`，同样计入 `finished_nodes`。否则这些节点永远停在 WAITING，实例永远等不到"全部终态"。

## 2. 机制总览

| 机制 | 解决 | 不解决 | 复杂度 |
| --- | --- | --- | --- |
| 唯一约束 | 重复创建（实例、调度、通知、尝试） | 状态机错误迁移 | 低 |
| 条件更新 | 并发抢占、幂等消费 | 跨多表的原子性 | 低 |
| 本地事务 | 同库多表原子性 | 跨服务一致性 | 低 |
| Transactional Outbox | 数据库与消息的最终一致 | 消息重复（需配合幂等） | 中 |
| 消费幂等 | 重复消息 | 外部副作用重复 | 中 |
| 租约（`lock_owner`/`lock_until`） | 多实例领取、崩溃自动释放 | 时钟漂移下的精确等待 | 中 |
| `SKIP LOCKED` | 批量任务领取吞吐 | 跨库协调 | 低 |
| 原子计数 + 条件终结 | 并发完成判定 | 计数逻辑本身的错误 | 低 |
| 定时对账 | 任意环节的"卡住" | 已发生的错误结果 | 中 |

## 3. 对账与恢复任务

| 任务 | 频率 | 判据 | 动作 |
| --- | --- | --- | --- |
| 到期调度扫描 | 1s | `schedule_job.enabled=1 AND next_fire_time <= NOW()` | 领取并创建执行实例 |
| 节点重试扫描 | 500ms | `node_execution.status='RETRY_WAIT' AND next_retry_at <= NOW()` | 置 READY 并投递 |
| READY 僵尸扫描 | 30s | `status='READY' AND updated_at < NOW()-60s` | 补写 Outbox 重投 |
| RUNNING 超时扫描 | 5s | `status='RUNNING' AND started_at + timeout_ms < NOW()` | 按可重试策略置 RETRY_WAIT 或 FAILED |
| 实例超时扫描 | 5s | `workflow_execution.status='RUNNING' AND deadline_at < NOW()` | 置 TIMED_OUT，未完成节点置 CANCELLED |
| 实例终结补偿 | 60s | `status='RUNNING' AND finished_nodes = total_nodes` | 补做终结判定 |
| Outbox 积压告警 | 30s | `status='PENDING' AND created_at < NOW()-5m` | 告警日志 |
| 死信巡检 | 5m | `dead_letter_record.status='PENDING'` | 告警日志 |

这些任务本身也必须**多实例安全**：用 `SKIP LOCKED` 或条件更新，绝不允许两个实例同时对同一行做同一动作。

## 4. 一致性边界

- **强一致**：单个服务的库内——业务记录与 Outbox 同事务。
- **最终一致**：跨服务——调度创建实例后，通知在实例终结后异步生成；允许秒级延迟。
- **不保证**：外部系统的副作用。只能通过幂等键尽力而为，并如实告诉用户"结果未知"。

## 5. 明确不使用的手段

| 手段 | 不用它的理由 |
| --- | --- |
| Redis 分布式锁做执行互斥 | 锁与数据库事务边界不一致；崩溃时依赖过期时间，存在脑裂窗口；正确性最终仍要靠数据库校验，锁只是性能优化 |
| 数据库悲观锁锁住整张节点表 | 并发度被串行化拖死，且长事务容易锁等待超时 |
| 两阶段提交 / XA | 引入协调者，故障面变大，且与"最终一致即可"的业务语义不匹配 |
| 依赖内存状态判断执行进度 | 进程一崩，全部丢失 |
