## 二、项目背景

项目名称：FlowForge

项目类型：智能任务编排与执行平台。

项目定位：用户可以通过 Web 页面配置自动化工作流，将多个任务节点按照依赖关系连接起来，由系统负责触发、调度、执行、重试、记录和通知。

典型场景：

用户创建一个每日执行的工作流：

1. 定时触发工作流。
2. 执行 HTTP 请求节点，获取外部数据。
3. 执行条件判断节点，根据结果决定是否继续。
4. 执行后续业务节点。
5. 如果某个节点执行失败，根据重试策略重新执行。
6. 保存工作流和节点的执行记录。
7. 向用户发送成功或失败通知。

项目重点不是简单实现 CRUD，而是通过具体业务展示微服务通信、任务调度、消息可靠性、并发控制和分布式环境下的一致性设计。

第一版以可控、可测试的模拟业务为主，不执行任意用户上传的代码，不开放任意 Shell 命令执行能力。

## 四、系统架构与服务边界

采用 Spring Cloud 微服务架构，第一版控制在 4～6 个核心业务服务，基础设施组件不计入业务服务数量。

### 4.1 Gateway 网关

职责：

- 统一对外暴露 API。
- 根据路由规则转发请求。
- 进行基础请求校验和限流。
- 传递请求追踪 ID。
- 对需要认证的接口执行统一认证校验。

注意：网关鉴权不能代替业务服务自身的权限校验。涉及资源归属和角色权限的操作，业务服务仍需独立验证。

### 4.2 用户服务 user-service

职责：

- 用户注册、登录和基本资料管理。
- JWT 签发与验证。
- 用户角色与权限管理。
- 账号状态管理。

要求：

- 密码使用安全的自适应哈希算法保存。
- 不在日志中输出密码、令牌或敏感认证信息。
- 对用户身份、账号状态和接口权限进行验证。

### 4.3 工作流服务 workflow-service

职责：

- 创建、修改和查询工作流。
- 管理工作流版本。
- 配置节点和节点依赖关系。
- 校验工作流定义。
- 发布可执行版本。
- 管理工作流启用和停用状态。

节点类型至少包括：

1. HTTP 请求节点。
2. 条件判断节点。
3. 模拟业务处理节点。
4. 通知节点。

工作流定义采用 DAG（有向无环图）模型。发布时必须检测循环依赖、无效节点引用、缺失依赖及非法配置。

工作流发布后生成不可变版本。正在执行的实例必须绑定启动时使用的工作流版本，不能因后续编辑而意外改变执行逻辑。

### 4.4 调度服务 scheduler-service

职责：

- 接收手动执行请求。
- 配合 XXL-JOB 触发周期任务。
- 扫描到期任务。
- 创建工作流执行实例。
- 防止重复调度。
- 处理调度失败后的恢复。

调度服务负责创建执行实例和安排任务，不负责实际执行所有业务节点。

必须设计多实例并发场景，不能假设系统永远只有一个调度节点。

### 4.5 执行服务 execution-service

职责：

- 从 RabbitMQ 接收待执行节点消息。
- 校验执行实例和节点状态。
- 检查前置依赖是否满足。
- 执行节点逻辑。
- 记录节点执行结果。
- 实现失败重试和退避。
- 调度后续可执行节点。
- 支持超时处理和失败恢复。

执行过程必须采用明确的状态机。禁止通过多个分散的布尔字段判断任务状态。

### 4.6 通知服务 notification-service

职责：

- 接收通知事件。
- 生成站内通知。
- 保存通知发送记录。
- 支持失败重试。
- 对重复通知进行幂等处理。

第一版只实现站内通知及模拟通知渠道，不依赖真实短信或付费邮件服务。

## 五、核心业务模型

### 5.1 工作流状态

工作流定义至少支持：

- DRAFT：草稿
- PUBLISHED：已发布
- DISABLED：已停用

工作流发布后生成独立版本号，执行实例引用具体版本。

### 5.2 工作流执行状态

建议采用：

- PENDING：等待执行
- RUNNING：执行中
- SUCCESS：执行成功
- FAILED：执行失败
- CANCELLED：已取消
- TIMED_OUT：执行超时

必须定义合法的状态迁移，使用条件更新或事务控制避免并发覆盖。

### 5.3 节点执行状态

建议采用：

- WAITING：等待依赖完成
- READY：可以执行
- RUNNING：执行中
- RETRY_WAIT：等待重试
- SUCCESS：执行成功
- FAILED：执行失败
- SKIPPED：跳过
- CANCELLED：已取消

只有依赖节点全部满足要求，当前节点才能进入 READY 状态。

对于条件分支，必须明确未选中分支的节点如何变为 SKIPPED，避免工作流永远无法结束。

### 5.4 执行流程

工作流执行时：

1. 校验用户是否有权执行该工作流。
2. 读取已发布的不可变版本。
3. 创建工作流执行实例。
4. 初始化节点执行记录。
5. 找出没有前置依赖的起始节点。
6. 创建待执行任务并发送调度事件。
7. 执行服务消费消息并执行节点。
8. 持久化节点执行结果。
9. 检查并推进后续节点。
10. 所有节点完成后更新工作流实例状态。
11. 发布通知事件。
12. 保留完整执行历史，支持故障排查。

每一步都需要考虑数据库事务、并发执行、消息重复投递和进程崩溃。

## 六、数据库设计

数据库按服务划分逻辑所有权。第一版可以使用同一个 MySQL 实例，但不同服务应使用独立数据库或至少独立的表集合，禁止直接读写其他服务拥有的业务表。

### 6.2 工作流服务

建议包含：

必须定义任务唯一键，防止多个调度实例重复创建同一个周期触发对应的执行实例。

### 6.4 执行服务

建议包含：

重要字段至少考虑：

- 主键
- 工作流 ID 和版本号
- 执行实例 ID
- 节点 ID
- 当前状态
- 重试次数
- 最大重试次数
- 下次重试时间
- 开始时间和结束时间
- 错误码和经过脱敏处理的错误信息
- 创建时间和更新时间
- 乐观锁版本号（确有需要时）

### 6.5 通知服务

建议包含：

- `notification_record`：通知记录
- `notification_delivery`：通知发送尝试记录

## 七、Redis 使用规范

Redis 只承担适合缓存和临时状态处理的工作。

可以用于：

- 需要短期保存的验证码。
- 登录失败计数和限流辅助。
- 热点工作流配置缓存。
- 短期调度协调信息。
- 非权威性的执行状态缓存。

要求：

1. 设置合理的 TTL。
2. 处理缓存穿透、击穿和雪崩风险。
3. 缓存更新策略必须与数据库状态保持合理一致。
4. Redis 不能成为工作流执行状态的唯一事实来源。
5. 不要把数据库唯一约束和事务控制替换为 Redis 锁。
6. 分布式锁需要明确租约、续期、所有权和异常恢复策略。
7. 缓存失效后系统仍应能够从数据库恢复必要的业务状态。

## 八、RabbitMQ 可靠性设计

RabbitMQ 负责任务分发和异步事件传递。

必须设计以下机制：

### 8.1 消息结构

消息至少包含：

- `eventId`
- `eventType`
- `executionId`
- `nodeExecutionId`
- `workflowVersion`
- `occurredAt`
- 必要的业务载荷

消息中不得携带密码、JWT 或其他不必要的敏感信息。

### 8.2 可靠投递

- 使用持久化队列和合理的消息持久化配置。
- 配置发布确认。
- 处理消息无法路由的情况。
- 正确处理消费者手动 ACK。
- 区分可重试错误和不可重试错误。
- 设置有限重试次数。
- 配置死信或延迟重试方案。
- 保留可查询的失败记录。

不能只依赖消息队列配置就宣称消息绝对不会丢失。

### 8.3 Transactional Outbox

当业务状态变更需要产生消息时：

1. 在同一个数据库事务中写入业务数据和 `outbox_event`。
2. 发布器扫描待发布事件。
3. 发布到 RabbitMQ。
4. 根据发布确认和路由结果更新事件状态。
5. 失败事件进行重试。
6. 消费者根据 `eventId` 或业务唯一键实现幂等。

必须处理数据库事务提交成功、消息尚未成功发布时应用进程崩溃的场景。

同时说明：Outbox 通常提供可恢复的至少一次投递能力，消费者仍必须能够处理重复消息。

### 8.4 消费幂等

- 为消息设计唯一事件 ID。
- 使用数据库唯一约束或条件状态更新。
- 防止重复消息重复创建执行记录。
- 防止重复推进同一个工作流节点。
- 对外部 HTTP 调用考虑业务幂等键。
- 明确 ACK 的时机和失败处理策略。

不能把"消息只消费一次"当成系统正确性的前提。

## 九、并发控制与分布式一致性

必须设计并测试以下场景：

1. 用户连续点击执行，重复创建工作流实例。
2. 多个调度实例同时扫描到期任务。
3. 两个消费者同时处理同一节点消息。
4. 节点执行完成，但进程在发送后续消息前崩溃。
5. 数据库提交成功，但 RabbitMQ 发布失败。
6. RabbitMQ 重复投递相同消息。
7. 工作流被停用时，仍有实例正在执行。
8. 工作流版本更新时，旧版本实例仍在执行。
9. 节点执行超时，但实际请求可能已经在外部系统成功。
10. 多个节点并发完成时，工作流实例状态发生竞争。

可使用以下手段组合解决：

- 数据库事务
- 唯一约束
- 条件更新
- 乐观锁
- 任务领取和租约
- Outbox
- 消费幂等
- 有限重试
- 定期对账和故障恢复

每种机制必须解释解决了什么问题、不能解决什么问题，以及失败后如何恢复。

禁止把所有问题都用 Redis 分布式锁解决。

## 十、任务重试与故障恢复

实现可配置的失败重试策略。

建议支持：

- 最大重试次数
- 初始退避时间
- 最大退避时间
- 指数退避
- 随机抖动（按需）
- 错误类型分类
- 手动重新执行
- 失败节点详情查询

重试延迟可以采用：

`delay = min(maxDelay, initialDelay * 2^retryCount)`

必须限制最大重试次数，防止任务无限重试。

对 HTTP 节点区分连接错误、超时、HTTP 错误码和业务校验错误。不能默认所有失败都适合重试。

如果调用外部接口后发生超时，无法确认对方是否已经完成操作。应明确该场景的处理策略，避免重复产生外部副作用。

## 十一、服务间通信与容错

### 同步调用

使用 OpenFeign 完成必要的服务间查询或校验。

要求：

- 配置连接超时和读取超时。
- 处理服务不可用。
- 对调用进行必要的日志记录。
- 使用 Resilience4j 实现有边界的熔断和重试。
- 仅对适合的操作启用重试，避免重复提交创建类请求。

### 异步调用

使用 RabbitMQ 执行耗时任务、发布执行事件和发送通知。

要求：

- 避免把所有操作都变成异步。
- 明确哪些操作需要同步返回结果。
- 明确异步执行的最终状态查询方式。
- 避免同步调用链无限增长。

### 服务发现

使用 Nacos 注册和发现服务。

要求：

- 通过服务名通信，不硬编码容器 IP。
- 配置文件区分本地开发和容器运行环境。
- 明确服务启动顺序和健康检查。
- 服务不可用时提供合理的失败响应。

## 十五、测试要求

### 15.2 集成测试

模拟：

- 消息发布失败。
- 消费者执行过程中崩溃。
- 消费者 ACK 前崩溃。
- 外部 HTTP 调用超时。
- Redis 短暂不可用。
- 任务进入死信队列。

每项测试必须记录预期结果、实际结果和测试方法。没有执行的测试只能标记为待验证，不得声称已经通过。

## 十六、工程目录与代码规范

采用 Maven 多模块工程，建议按职责组织：

- `flowforge-common`：公共异常、响应模型和工具。
- `flowforge-gateway`：API 网关。
- `flowforge-user-service`：用户与权限。
- `flowforge-workflow-service`：工作流定义和版本。
- `flowforge-scheduler-service`：定时调度。
- `flowforge-execution-service`：执行引擎。
- `flowforge-notification-service`：通知中心。
- `flowforge-frontend`：Vue 前端。
- `deploy`：Docker Compose、数据库初始化和部署配置。
- `docs`：架构文档、接口文档和测试报告。

如果公共模块可能造成业务服务之间的紧耦合，应控制其内容，不要将所有业务实体、Mapper 和 Service 都放进公共模块。

编码要求：

- 命名清晰，职责单一。
- Controller 不承载复杂业务逻辑。
- Service 负责业务流程编排。
- Mapper 负责数据库访问。
- DTO、VO 和持久化实体按需分离。
- 使用参数校验。
- 统一异常处理。
- 避免不必要的继承和抽象。
- 不提交密码、真实密钥或生产环境凭据。
- 不使用大量硬编码业务参数。
- 不通过捕获异常后忽略来掩盖错误。
