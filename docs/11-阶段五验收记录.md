# 11 阶段五验收记录：前端开发与通知服务

> 记录日期：2026-10-28。只记录**实际执行过**的验证。

## 1. 交付内容

### 通知服务 `flowforge-notification-service`

| 能力 | 说明 |
| --- | --- |
| 消费 `workflow.finished` | 手动 ACK，处理失败只记录日志——通知是旁路能力，不阻塞主链路 |
| 幂等生成 | `notification_record.uk_source_event` 挡住重复消息 |
| 投递记录 | `notification_delivery` 记录站内渠道的投递结果 |
| 查询与已读 | 列表、未读数、标记已读（已读的重复标记幂等） |

### 前端 `flowforge-frontend`

| 页面 | 内容 |
| --- | --- |
| 登录 / 注册 | 表单校验、加载态、错误提示、登录后跳回原路径 |
| 工作流列表 | 搜索、分页、发布、启停、执行、跳转执行记录 |
| 工作流编辑 | 基本信息、节点表格、按类型切换的节点配置表单、依赖表（含 TRUE/FALSE 分支）、校验、保存草稿、发布、版本历史 |
| 执行记录 | 按状态筛选、进度、跳转详情 |
| 执行详情 | 概要、节点状态与失败原因、抽屉查看每次尝试（含请求/响应摘要与「结果未知」标记） |
| 通知中心 | 未读筛选、标记已读、跳转对应执行 |

技术栈：Vue 3.5 + TypeScript + Vite 7 + Element Plus 2.9 + Pinia 3 + Vue Router 4 + Axios。

## 3. 过程中发现并修复的问题

| 问题 | 根因 | 修复 |
| --- | --- | --- |
| `127.0.0.1:5173` 访问失败 | Vite 默认只监听 `[::1]`，IPv4 访问不通 | 配置 `host: true` 监听所有 IPv4 接口 |
| 发布按钮的类型推断报错 | 用逗号表达式在一行里「保存 + 取 id」，可读性差且类型收窄失败 | 拆成显式分支，先保存再取 id |
| 节点 key 改名后依赖断裂 | 编辑节点时只替换了节点，边的引用还指向旧 key | 保存节点时同步重写边的端点 |
| 通知消费失败会阻塞队列 | 无重试上限的 requeue 会让故障消息反复投递 | 明确取舍：ACK 并记录日志，不重投 |

## 4. 设计说明

**为什么通知不重试**

通知是旁路能力：漏一条站内通知，用户仍然可以在「执行记录」里看到结果。
为它引入延迟队列和重试上限，会让非关键路径的故障挤占关键路径的资源。
真正不能妥协的是幂等——同一事件重复投递绝不能产生第二条通知。

**为什么前端用表单而不是拖拽画布**

DAG 本质是「节点 + 有向边」，用两张表格就能完整表达，而且对键盘操作、屏幕阅读器、
窄屏都更友好。拖拽画布是交互复杂度，不是业务复杂度，与要演示的可靠性设计无关。

**前端不做权限判断**

路由守卫只处理「没登录就跳登录页」。资源归属、角色权限一律由后端判定——
隐藏按钮只是体验优化，不构成安全边界。

## 5. 已知问题

| 问题 | 影响 | 计划 |
| --- | --- | --- |
| 未做浏览器端的手工操作验证 | 页面交互细节（如表单联动）尚未肉眼确认 | 需人工在浏览器走一遍完整流程 |

| 无前端自动化测试 | 回归靠手工 | 第一版不承诺 |
