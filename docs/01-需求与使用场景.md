# 01 需求与使用场景

## 1. 产品定位

FlowForge 是一个**智能任务编排与执行平台**。用户把若干任务节点按依赖关系连成 DAG 工作流，平台负责触发、调度、执行、重试、留痕与通知。

与普通"定时脚本平台"的区别在于，本项目的设计重心在**执行过程中的可靠性**：

- 节点失败后按策略退避重试，而不是一失败就整体放弃；
- 进程在任意环节崩溃后，系统靠数据库状态自行恢复，而不是依赖人工修数据；
- 同一份消息被重复投递、同一个按钮被连点两次、两个调度实例同时扫到同一条任务，都不会产生重复的业务结果。

## 2. 用户角色

| 角色 | 权限范围 |
| --- | --- |
| `ADMIN` | 查看全部用户的工作流与执行记录；管理用户账号状态；查看全局调度与死信情况 |
| `USER` | 创建、编辑、发布、执行、停用**自己**的工作流；查看自己工作流的执行记录与通知 |

权限校验分两层：网关只判断"请求是否携带有效身份"，**资源归属**（这条工作流是不是你的）由业务服务在查询、修改、执行、取消等每个动作上独立校验。前端隐藏按钮只是体验优化，不构成安全边界。

## 4. 典型场景走查

### 场景 A：每日数据同步工作流

用户配置一个每天 08:00 执行的工作流：

```
[HTTP 拉取数据] → [条件判断：数据非空?] --TRUE--> [模拟业务处理] → [发送通知]
                                        --FALSE-> [发送跳过通知]
```

执行过程：

1. XXL-JOB 在 08:00 触发调度任务，调度服务生成 `schedule_execution` 记录（唯一键 `job_id + fire_time`，多实例竞争时只有一个能插入成功）。
2. 调度服务调用工作流服务读取已发布版本的节点与边，创建 `workflow_execution`，状态 `RUNNING`。
3. 初始化各节点执行记录：起始节点 `READY`，其余 `WAITING`。
4. 起始节点写入 `outbox_event`，发布器投递 `node.ready` 消息到 RabbitMQ。
5. 执行服务消费消息，以条件更新把节点从 `READY` 抢占为 `RUNNING`，执行 HTTP 请求。
6. HTTP 节点成功，写入 `execution_attempt`，节点置 `SUCCESS`，在同一事务中判定后继节点是否可进入 `READY`。
7. 条件节点比较结果：TRUE 分支继续，FALSE 分支的所有下游节点被标记 `SKIPPED`。
8. 所有节点到达终态后，工作流实例置 `SUCCESS` 或 `FAILED`，并写入 `workflow.finished` 事件。
9. 通知服务消费事件，生成站内通知（以 `source_event_id` 唯一约束保证重复消息不会产生重复通知）。

### 场景 B：节点失败与重试

HTTP 节点首次调用返回 502：

1. 执行服务记录一次 `execution_attempt`（失败，错误码 `HTTP_502`），节点置 `RETRY_WAIT`，按指数退避计算 `next_retry_at`。
2. 重试扫描器（或延迟队列消息）到期后把节点置回 `READY` 并重新投递。
3. 重试次数达到上限仍失败 → 节点置 `FAILED`，工作流实例置 `FAILED`，发布失败通知。

4xx 业务错误不重试；连接超时属于**结果未知**，按单独策略处理（见 [06-并发与一致性方案](06-并发与一致性方案.md)）。

### 场景 C：进程崩溃后的恢复

节点成功、数据库事务已提交，但发布后继节点消息前进程被 kill：

- 业务数据与 `outbox_event` 在同一事务中已提交，消息并未真正发出；
- Outbox 发布器在下一轮扫描中发现 `status=PENDING` 的事件并补发；
- 若消息其实已经发出但进程未及时标记 `SENT`，会重复投递一次，由消费端幂等吸收。

## 5. 范围边界

### 第一版实现

- 4 类节点：HTTP 请求、条件判断、模拟业务处理（可配置耗时与失败率）、通知。
- 手动执行与 cron 定时执行。
- 节点级重试、退避、超时。
- 站内通知与模拟渠道。
- 执行历史、节点明细、尝试记录查询。
- Docker Compose 一键拉起全部依赖。

### 第一版明确不做

| 不做 | 原因 |
| --- | --- |
| 执行用户上传的任意代码 / Shell 命令 | 沙箱与权限边界不是本项目要演示的重点，风险不可控 |
| 真实短信、邮件服务商对接 | 引入外部付费依赖，且不影响要演示的可靠性设计 |
| 复杂的拖拽式流程设计器 | 第一版用表单 + 依赖表即可表达 DAG，交互复杂度与设计目标无关 |
| 分布式事务（Seata 等） | 跨服务一致性通过本地事务 + Outbox + 幂等解决，不引入额外中间件 |
| 多租户隔离 | 与项目主题无关 |
| 大流量压测与性能调优 | 设计上保证正确性，性能只做基本验证 |

## 6. 非功能需求

| 维度 | 要求 |
| --- | --- |
| 可运行性 | `docker compose up` 后按文档步骤可完成一次完整演示，不需要手工装依赖 |
| 数据正确性 | 任何节点的状态迁移可追溯到 `execution_attempt` 与 `execution_event` |
| 幂等性 | 重复提交、重复消息、重复扫描不产生重复业务记录 |
| 可恢复性 | 进程在投递、消费、推进任意环节崩溃后，系统能自行收敛到正确状态 |
| 安全性 | 密码自适应哈希、JWT 短期有效、日志与消息体不含明文凭证 |
| 可观测性 | 全链路 `traceId`，执行 ID / 节点执行 ID 出现在关键日志中 |
| 可测试性 | 关键并发与故障场景有可重复执行的测试用例 |
