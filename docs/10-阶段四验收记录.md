## 2. 执行链路的变化

```
改造前（阶段三）：
  节点完成 → 线程池直接提交下一个节点

改造后（阶段四）：
  节点完成 ──同一事务──▶ 节点终态 + outbox_event(PENDING)
                            │
                            ▼
                     发布器扫描 → RabbitMQ → Confirm
                            │            │
                          SENT        失败则退避重发
                            │
                            ▼
                 消费者（手动 ACK）→ 抢占节点 → 执行
```

## 5. 过程中发现并修复的问题

| 问题 | 根因 | 修复 |
| --- | --- | --- |
| `outbox_event` 更新报错 | 建表时漏了 `updated_at` | 补字段与脚本 |
| **毒消息死信记录写入失败** | `dead_letter_record.payload` 是 JSON 列，而毒消息本身就不是合法 JSON | 改为 `TEXT`，并注明"不保证是合法 JSON" |
| **手工 SQL 插入的 XXL-JOB 任务触发时报 NPE** | admin 的 `/jobinfo/add` 接口会补齐内部字段，直接插库拿不到 | 改用 admin 接口创建（表单参数，非 JSON） |
| XXL-JOB 执行器组标题插入失败 | `xxl_job_group.title` 只有 `varchar(12)` | 标题改用短英文 |
| 调度服务启动失败 `NoClassDefFoundError: RxJava3FallbackDecorator` | `resilience4j-spring-boot3` 的 fallback 自动配置会反射扫描 RxJava3 装饰器 | 引入 `resilience4j-rxjava3`，并用 BOM 统一版本 |
| Feign 拦截器拿不到 `JwtTokenService` | 写在 `@FeignClient(configuration=...)` 里，那是子上下文 | 移到主容器，对全部 Feign 客户端生效 |
| `Message.getDeliveryTag()` 不存在 | deliveryTag 在 `MessageProperties` 上 | 改 `getMessageProperties().getDeliveryTag()` |

## 6. 设计要点

**为什么重试有两层，且都要保留**

| 层级 | 触发 | 载体 | 兜底 |
| --- | --- | --- | --- |
| 节点级重试 | 节点业务失败 | `RETRY_WAIT` + `next_retry_at` | 扫描器 |
| 消息级重试 | 消费过程异常 | 延迟队列（5s/30s/2m） | 死信 + `dead_letter_record` |

延迟队列是"加速器"，扫描器是"兜底"：消息丢了扫描器还能把节点的 `RETRY_WAIT` 捡回来继续推进。**数据库始终是事实来源。**

**为什么不用 `basicNack(requeue=true)`**

数据库抖动时会让同一条消息在队列里无限打转，占满消费线程并打爆日志。所有重试都必须经过延迟队列并带次数上限。

**为什么周期任务不改 @Scheduled**

`@Scheduled` 在多实例下每个实例各跑一遍。XXL-JOB 由调度中心统一决定谁来跑；即便如此，真正的防重复仍由 `schedule_execution.uk_job_fire` 唯一键兜底——不假设调度框架永远只触发一次。
